## 2. 기존 문제의 원인

1. 본체는 assistant 기준 위치, 마스코트는 별도 span에서 ±12px(모바일 ±4px)로 부유했다. 둘의 간격이 계속 변했고 꼬리가 없어 별도 안내 상자로 보였다.

기존의 표시 전 충돌 검사, 가까운 안전 위치가 없을 때 회차 생략, 같은 회차 재등장 금지는 유지한다.

## 3. 위치·거리·꼬리

### 구현

- 말풍선을 항상 존재하는 absolute `hint-anchor` 안에 넣었다. anchor와 기존 `mascot-float`는 같은 3.2초 keyframes/부유 거리로 함께 움직인다. 패널 열기/X 닫기에도 anchor를 다시 만들지 않아 부유 위상이 재시작되지 않는다.
- 기본 right/bottom은 desktop **26/102px**, 900px 이하 **8/66px**다. 실제 assistant/launcher 크기를 기준으로 배치하며 화면 전체의 임의 좌표를 계산하지 않는다.
- 가까운 후보는 desktop (26,102)→(18,102)→(-8,102)→(26,110), 모바일 (8,66)→(16,66)→(0,66)→(8,74)뿐이다. 회차 중에는 위치를 다시 옮기지 않는다. 공간이 없으면 해당 회차를 생략한다.
- `::before` 12×9px 외곽과 `::after` 10×8px 내부의 작은 삼각형을 오른쪽 아래에 겹쳤다. 기존 테두리 #777771/배경 #292927를 이어 쓰고 polygon(0 0,100% 0,78% 100%)으로 절제된 꼬리를 만든다.
- 꼬리의 right는 `launcherWidth / 2 - bubbleRight - 3`이다. 후보 위치가 달라져도 끝이 마스코트 중심축을 향한다. 색·글자14px·행간1.5·그림자·X 버튼 크기는 유지했다.
- 충돌 사각형은 본체만이 아니라 꼬리 바깥 길이8px, 등장 이동6px, 전체 부유 범위와 안전 여백을 예약한다. viewport 여백도 검사한다. 꼬리·사진·버튼을 위해 위로 무제한 밀어 올리지 않는다.

## 4. 등장·퇴장과 상태 처리

| 상황 | 최종 처리 |
|---|---|
| 최초/정규 회차 표시 전 | 현재 콘텐츠/이미지/조작 영역과 본체+꼬리를 검사. 안전하지 않으면 처음부터 opacity0, 해당 회차 생략 |
| 안전한 회차 등장 | opacity0→1 / translateY6px→0, 220ms ease |
| 정상 3초 종료 | opacity1→0 / translateY0→6px, 160ms ease |
| 표시 중 스크롤 충돌 | 위치 고정. 즉시 pointer-events:none/aria-hidden/tabIndex-1로 전환하고 같은160ms fade-out |
| X 닫기 | sessionStorage를 즉시 저장하고 같은160ms fade-out. DOM을 즉시 제거하지 않음 |
| 퇴장 뒤 같은 회차 | skipped 잠금을 유지. 스크롤 복귀/역방향/안전 공간 재확보로 재등장하지 않음 |
| 다음 정규 회차 | 기존20초 interval에서만 새 회차/안전 검사를 시작 |
| reduced-motion | 공유 부유·공간 이동 없음. opacity0.01ms. 보이는 상태의 duration 우선순위도 명시적으로 재정의 |

별도의 퇴장 timeout/state 머신을 추가하지 않았다. 기존 visible/safe 상태로 CSS를 전환하고 DOM을 유지하므로 3초 타이머와 퇴장 타이머가 서로 재시작하지 않는다. 패널을 사용자가 열었을 때 자동 충돌 정책이 패널을 닫지 않는다.

움직이는 콘텐츠가 접근하면 안전 여백에서 퇴장을 시작한다. 빠른 스크롤은 fade 중 콘텐츠가 일시적으로 뒤에 들어올 수 있지만 자동 안내는 즉시 클릭을 통과시키고 제자리에서 퇴장한다. fade를 위해 콘텐츠를 가리며 위치를 따라 이동하지 않는다.

### 실제 프레임 비교

표는 첫 숨김 상태가 관찰된 프레임부터 opacity<0.001인 프레임까지다. 스타일에 설정한 시간과 브라우저의 이미지 paint/프레임 지연을 구분한다.

| 해상도 | 정상 종료 ms | 사진 충돌 종료 ms | X 닫기 ms |
|---|---|---|---|
| 1920×1080 | 159.80 | 249.90 | 159.90 |
| 1440×900 | 160.10 | 159.90 | 158.30 |
| 1024×768 | 159.40 | 159.90 | 159.80 |
| 768×1024 | 159.90 | 160.10 | 159.90 |
| 390×844 | 160.00 | 159.90 | 159.90 |

200ms 시제품은 사진 진입 부하가 겹칠 때 약290ms까지 관찰돼 최종 퇴장을160ms로 줄였다. 최종 표본에서는 정상/X 약158–160ms, 사진 충돌 약160–250ms였고 모든 경우 중간 opacity와 DOM 유지가 확인됐다. 브라우저 부하가 큰 환경까지 이 최대값을 보장하는 수치는 아니다. 시제품 기록은 `motion-200ms.json`에 보존했다.

실제 hit-test에서도 퇴장 중 말풍선 중앙의 `elementFromPoint`는 assistant가 아닌 아래 콘텐츠였다. 1920px은 about-section,390px은 개인 프로젝트 요소를 반환했다. 버튼 tabIndex는 둘 다-1, pointer-events는 none, DOM은 연결된 상태였다. 눈에 보이지 않는 자동 안내가 포커스나 클릭을 가로채지 않는다.

## 5. 기존 자동 표시와 수동 챗봇

타이머 effect의 코드(최초 timeout/interval/숨김 timer/cleanup)는 시작 소스와 **문자열 비교로 동일**하다. 충돌로 인한 fade-out은 이를 재시작하지 않는다.

| 항목 | 실제 측정 또는 검증 |
|---|---|
| 최초 timeout 생성→실행 | 5068.20ms (설정5000ms) |
| 회차 간격 | 20003.80ms / 19998.80ms (설정20000ms) |
| 정상 visible 상태 지속 | 3003.60ms / 3005.40ms / 3000.70ms (설정3000ms) |
| 문구 | 프로젝트→역할→기술, 기존3개 순환 |
| 충돌 다음 회차 | 원래 interval callback 실행으로 다시 표시. interval 새 등록 없음 |
| 수동 패널 | 5해상도 모두 열기/추천 질문→답변2개 추가/사진으로 이동해도 패널 유지/ESC 닫기 통과 |
| X/sessionStorage | 즉시 true 저장. reload 뒤 말풍선 DOM은 남지만 aria-hidden=true/opacity0. 수동 챗봇 사용 가능 |

3초는 정규 종료를 시작하는 시점이며 그 뒤160ms 전환이 따른다. 수동 패널을 열고 닫을 때의 기존 effect pause/cleanup 동작도 그대로다. 실제 5/20/3 주기는 벽시계로 측정했고, 위치/퇴장 반복 검사는 QA에서 원래 callback을 실행한 별도 검사다. 제품 타이머를 빠르게 바꾸거나 새 타이머를 만든 결과가 아니다.
